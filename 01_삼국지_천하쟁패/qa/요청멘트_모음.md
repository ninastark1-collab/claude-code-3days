# 개발 담당에게 보내는 멘트 모음 (상황별, 복사해서 그대로)

> 원칙: 멘트는 짧게, 자세한 건 파일에 둔다. 개발 친구는 바쁘다. **"무엇을 · 어느 파일에서 · 어떤 순서로 · 언제까지 회신"** 네 가지만 말한다.
> 작업 규칙 전문은 `qa/개발자_요청멘트.md`(처음 한 번), 요청서 본문은 `qa/requests/사이클<N>_개발.md` 에 있다.

```
1. 작업 규칙은 qa/개발자_요청멘트.md 에 있어. 처음 한 번만 끝까지 읽어 줘.
   핵심만 말하면 이거야.
   - 폰이 기준이야.
   - 이 게임은 돈 받고 파는 상품이야.
   - 요청서 번호 하나에 수정 하나씩 해 줘.
   - 회신 전에 자가 확인 4종과 빌드를 꼭 통과시켜 줘.
   - qa/ 안에서는 qa/requests/ 에 회신만 써 줘.
2. 내가 테스트를 마치면 qa/requests/사이클1_개발.md 를 올릴게. 그때 다시 말할게.

   급한 수정이 있으면 먼저 말해 줘.
```

## ③ 요청서를 보낼 때 (매 사이클)

```
사이클 <N> 요청서 올렸어: qa/requests/사이클<N>_개발.md

- 이번 빌드: <버전 / 빌드 시각>
- 요약: S1 <n>건 · S2 <n>건 · S3 <n>건 · 확인 질문 <n>건
- 꼭 먼저 해 줘: <QA-DEV-xx 제목>, <QA-DEV-yy 제목>
  (S1은 출시를 막는 문제야. 각 항목의 PM 번호는 qa/망한이유_요건.md 에서 이유를 볼 수 있어)
- 회신은 qa/requests/사이클<N>_개발_회신.md 에 맨 아래 양식대로 써 줘.
  S1·S2만 끝나도 먼저 회신해 줘. S3는 다음 사이클로 넘겨도 돼.
- 방법은 네 판단대로 해. 요청이 틀렸다고 생각하면 "보류 + 이유"로 답해 줘.
```

## ④ 회신을 받고 재검증을 마친 뒤

```
사이클 <N> 회신 재검증 끝났어. 결과는 다음 요청서 맨 아래 "지난 사이클 재검증 결과"에 있어.

- 해결 <n>건 · 미해결 <n>건 · 회귀 <n>건
- 회귀(고쳤는데 다시 깨진 것): <QA-DEV-xx>. 이건 다음 사이클 최우선이야.
- 보류로 답한 <QA-DEV-xx>: <받아들임 / 사용자 결정 필요 / 다시 요청(이유)>
- 다음 요청서: qa/requests/사이클<N+1>_개발.md
```

```
재현: <한 줄>

```

## ⑥ 회신 규칙을 안 지켰을 때 (부드럽게, 근거와 함께)

```
회신 고마워. 근데 두 가지만 맞춰 줘. 이게 지켜져야 내가 빨리 재검증할 수 있어.
- <예: npm run build 가 실패해서 이번 빌드는 검증을 못 했어 → 빌드 통과한 상태로 다시 알려 줘>
- <예: QA-DEV-03, 05를 한 커밋으로 고쳐서 무엇이 무엇을 고쳤는지 구분이 안 돼 → 회신 표에 번호별로 나눠 적어 줘>
```
