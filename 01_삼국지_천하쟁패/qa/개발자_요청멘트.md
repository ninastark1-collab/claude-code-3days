# 개발 담당에게 보내는 요청 멘트 (복사해서 그대로 전달)

---

지금부터 이 게임은 출시 전 **최종 검증 단계**에 들어가. 전담 테스터(QA 세션)가 테스트를 최소 10회 반복하면서 문제를 찾아 수정 요청서를 보낼 거야. 너는 그 요청을 반영하고 회신하면 돼. 이 과정을 출시 판정이 날 때까지 반복할 거야. 아래 규칙대로 해 줘.

## 1. 가장 중요한 전제: 폰이 기준이다

- 이 게임의 최종 목표는 **핸드폰(가로 844×390 기준)** 이야. PC·웹에서 잘 돌아가도 폰에서 이상하면 실패야.
- 그래서 고칠 때마다 폰 크기, 터치 조작, 보급형 폰 성능을 먼저 생각해 줘. 마우스 올리기(hover)에만 의존하는 기능, 작은 터치 영역, 백그라운드 전환 시 진행 손실은 모두 버그야.
- 폰 관련 기준은 `qa/체크리스트_모바일.md` 에 있어.
- 이 게임은 **돈 받고 파는 상품**이야. 테스터는 "이 값을 내고 샀다면 환불하지 않겠는가"로 판정해. 판정 1순위 기준은 `qa/망한이유_요건.md`(PM 번호)야. 요청서 항목에 PM 번호가 붙어 있으면 그게 왜 출시를 막는지 거기서 확인해 줘.
- 지금 **폰용 빌드(APK/AAB·iOS)가 없어서** 판매 자체가 불가능한 상태야(PM-K1, 체크리스트_개발 D8). 폰 빌드 방식을 정하는 게 가장 먼저야.

## 2. 요청서와 회신이 오가는 방법

- 요청서는 `qa/requests/사이클<N>_개발.md` 로 와. N은 1부터 올라가.
- 너는 같은 폴더에 `qa/requests/사이클<N>_개발_회신.md` 로 회신해 줘.
- 버그 번호(`QA-DEV-xx`)는 사이클이 바뀌어도 같은 버그면 같은 번호야. 회신도 이 번호로 해 줘.
- `qa/` 폴더의 다른 파일(체크리스트, 스크립트, 결과)은 **고치지 마.** 테스트 기준이 흔들리면 검증이 무의미해져. `qa/requests/` 에 회신 파일을 쓰는 것만 해 줘.

## 3. 반영 순서

1. **S1 → S2 → S3 → S4** 순서로 고쳐 줘. S1(진행 불가·튕김·세이브 손실·저작권)과 S2(핵심 기능 오류·A등급 실패·폰에서 못 쓰는 것)가 먼저야.
2. **한 번호에 한 수정.** 여러 버그를 한 번에 뭉뚱그려 고치지 마. 그래야 무엇이 무엇을 고쳤는지 추적할 수 있어.
3. 고치다가 다른 곳이 깨질 수 있으니, 회신하기 전에 최소한 이것들은 직접 돌려서 통과를 확인해 줘.
   ```
   npx tsc --noEmit
   npx vitest run
   npx tsx scripts/validate-data.ts
   bash qa/scripts/run-auto.sh quick
   ```
   `run-auto.sh quick` 결과에 새 FAIL이 생겼다면 그것도 회신에 적어 줘.
4. 고친 버그마다 **같은 버그가 다시 생기지 않게 막는 테스트**를 `tests/` 에 하나씩 추가해 주면 가장 좋아. 어려운 항목은 "테스트 못 넣음, 이유: …"라고만 적어 줘.
5. 회신할 때 빌드가 **반드시 성공하는 상태**여야 해 (`npm run build`). 고치는 중간 상태로 회신하지 마. 빌드가 안 되면 테스터는 그 사이클 전체를 S1로 판정할 수밖에 없어.
6. 회신할 때마다 `package.json` 의 version을 올리거나(예: 0.1.0 → 0.1.1), 최소한 회신서에 빌드 시각을 적어 줘. 테스터는 그 빌드로 재검증해.

## 4. 네가 판단해도 되는 것, 하면 안 되는 것

- **판단해도 됨:** 고치는 방법, 수치 조정 폭, 코드 구조. 요청서의 "수정 제안"은 참고일 뿐이야. 더 좋은 방법이 있으면 그걸로 해.
- **반대해도 됨:** 요청이 잘못됐거나 설계와 충돌한다고 생각하면 고치지 말고 "보류 + 이유 한두 줄"로 회신해 줘. 테스터가 다시 판단해서 사용자에게 올릴 거야.
- **방침 질문:** 요청서 끝의 "확인해 주세요" 항목(예: 강을 수군 없이 건너도 되는지, 도시가 0개면 바로 멸망하는지)은 버그가 아니라 설계 결정이야. 지금 설계 의도를 한두 줄로 답해 주면 돼. 바꿀지는 사용자가 정해.
- **하면 안 됨:**
  - 화면 디자인(배치·색·글꼴·크기·연출)을 네 마음대로 바꾸는 것. 그건 디자이너 담당이야. 담당이 `디자인`인 항목은 너에게 오지 않아. 다만 폰에서 **동작**이 안 되는 문제(버튼이 안 눌림, 화면 밖으로 나감, 백그라운드 저장 없음)는 네 담당이니 고쳐 줘.
  - 시나리오 데이터·문장(장수 배치, 능력치, 이벤트 문구)을 임의로 바꾸는 것. 시나리오 담당 항목이야. 단, 조사 자동 처리 함수처럼 **코드가 필요한 부분**은 요청서에 개발 담당으로 와.
  - `개발자_전달서.md` 의 C등급(군단제, 연대기, 설전 등) 기능을 이번 기회에 슬쩍 같이 넣는 것. 범위가 늘면 버그도 늘어나.
  - 테스트를 통과시키려고 테스트나 검사 기준을 바꾸는 것.

## 5. 회신서 형식

```
# 사이클 <N> 개발 회신

빌드: <버전 또는 빌드 시각>   npm run build: 성공
자가 확인: tsc ✅ / vitest ✅ (테스트 n개 추가) / validate-data ✅ / run-auto quick: FAIL n건 (새로 생긴 것: …)

| 번호 | 상태 | 한 일 (한두 줄) | 테스트 추가 | 확인 방법 |
|---|---|---|---|---|
| QA-DEV-01 | 반영 | … | tests/engine.test.ts "…" | … |
| QA-DEV-02 | 보류 | (이유) | — | — |
| QA-DEV-03 | 일부 반영 | 무엇까지 했고 무엇이 남았는지 | | |

## 방침 질문 답변
- …

## 테스터에게 알릴 것
- 이번 수정으로 바뀐 동작, 같이 봐 줬으면 하는 곳, 재현이 안 된 항목
```

## 6. 끝나는 기준

- 사이클마다 테스터가 **재검증 결과**(해결 / 미해결 / 회귀)를 요청서 맨 아래에 붙여 줄 거야. 회귀(고쳤는데 다시 깨짐)는 다음 사이클 최우선이야.
- S1·S2가 0건이 되고, 실제 폰(보급형 안드로이드 + 아이폰)에서도 통과하면 테스터가 "출시 가능" 판정을 내려. 그때까지 반복하자.
