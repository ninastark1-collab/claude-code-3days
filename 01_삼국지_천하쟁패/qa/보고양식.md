# 보고 양식

## 1. 버그 1건 양식

```
[QA-<담당 약자>-<번호>] <한 줄 제목: 어디서 무엇이 어떻게 틀림>
- 담당: 개발 | 시나리오 | 디자인   (참조: <다른 담당>)
- 심각도: S1 치명 | S2 중대 | S3 보통 | S4 사소
- 근거: <체크리스트 ID / 설계노트 장 / 전달서 A·B 항목 / 디자인 문서 화면 ID>
- 망한 이유 요건: <PM-xx (P0/P1/P2) — 해당하면 반드시 적는다. P0면 심각도 S1>
- 빌드: <스냅숏 시각 또는 버전>   환경: <웹 스냅숏 | 설치본> <1280×800 | 844×390>
- 재현 절차:
  1. 
  2. 
  3. 
- 기대 결과:
- 실제 결과:
- 재현율: <예: 5/5>   시드/세이브: <qa/results/.../save_xxx.json>
- 증거: <스크린샷 경로, 로그 발췌>
- 수정 제안: <한두 줄. 방법은 담당 판단에 맡김>
```

담당 약자: DEV(개발), SCN(시나리오), DSN(디자인). 번호는 사이클이 바뀌어도 유지한다(같은 버그 = 같은 번호).

## 2. 담당별 보고서 양식

```
# <담당> 수정 요청서 — 사이클 <N> (<날짜>)

빌드: <스냅숏 시각>   검증 범위: <체크리스트·세션 목록>
요약: S1 <n>건 · S2 <n>건 · S3 <n>건 · S4 <n>건

## 먼저 고쳐 주세요 (S1·S2)
<버그 양식들>

## 출시 전에 고치면 좋은 것 (S3)
<버그 양식들>

## 나중에 (S4·제안)
<한 줄씩>

## 확인해 주세요 (질문·정책 결정)
- <예: 건업·허창 같은 후대 지명을 시나리오 연도에 맞게 바꿀지 방침을 정해 주세요>

## 지난 사이클 재검증 결과
| 번호 | 제목 | 판정 (해결/미해결/회귀) |
```

개발 담당에게 보낼 때는 `개발자_전달서.md` 5장 형식에 맞춰 A·B 항목별로도 묶는다:

```
[A2] 세이브 버전 번호
- 검증 결과: 통과 / 실패
- 확인한 방법: (한두 줄)
- 실패 내용: QA-DEV-xx 참고
```

## 3. 출시 판정 요약 (사용자에게)

```
# 출시 판정 — 사이클 <N>

판정: 출시 가능 / 출시 보류

| 조건 | 상태 |
|---|---|
| S1 0건 | ✅ / ❌ (n건) |
| S2 0건 | |
| A1~A7 전부 통과 | |
| 스모크 테스트 | |
| 설치본 검증 | |
| 자동 검사 실패 0 | |

남은 조건: <출시 보류일 때 무엇이 해결되면 되는지>
담당별 현황: 개발 n건 / 시나리오 n건 / 디자인 n건
다음 사이클: <재검증할 것>
```
